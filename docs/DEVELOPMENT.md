# 开发与贡献规范

本文档定义 Local Console Hub 在早期开发阶段的工程约束。目标不是建立繁琐流程，而是避免核心行为在快速迭代中变得不可预测。

## 1. 开发优先级

优先顺序：

1. **终端交互正确性**
2. **进程生命周期安全**
3. **会话状态可理解**
4. **日志行为可预测**
5. **低资源占用**
6. **UI 易用性**
7. **扩展功能**

任何漂亮 UI 都不能以牺牲 PTY 正确性、进程安全或日志边界为代价。

## 2. Windows 优先

早期版本以 Windows 为第一目标平台。

需要优先验证：

- ConPTY；
- PowerShell / pwsh / CMD；
- Windows 进程树；
- Ctrl+C / Ctrl+Break 等控制行为；
- Unicode；
- 路径与工作目录；
- 系统托盘；
- DPI 与窗口缩放。

跨平台抽象可以保留，但不要为了尚未支持的平台牺牲 Windows MVP 的稳定性。

## 3. 模块边界

无论最终使用何种语言/框架，核心逻辑应尽量分层：

### Session Core

负责：

- 会话定义；
- 状态机；
- 生命周期；
- 配置；
- run_id。

### PTY Layer

负责：

- 创建 PTY；
- 输入输出；
- resize；
- 控制序列；
- 关闭与退出通知。

UI 不应直接操作底层 PTY 句柄。

### Process Layer

负责：

- 启动；
- PID；
- 子进程；
- 优雅停止；
- 强制结束；
- 退出码。

### Logging Layer

负责：

- 内存缓冲；
- 持久化策略；
- external log；
- 文件组织；
- rotation；
- retention。

PTY 层不应因为“有输出”就自动决定写文件。

### Status / Health Layer

负责：

- 进程状态；
- 端口检查；
- HTTP health；
- Busy / Ready 等后续扩展。

### UI Layer

负责展示和用户操作，不应成为状态真相来源。

### Tray Layer

负责：

- 隐藏；
- 恢复；
- 快速状态；
- 真正退出入口。

## 4. 状态真相原则

状态必须来自核心层，而不是 UI 猜测。

例如：

错误：

```text
按钮是灰的，所以程序应该在运行。
```

正确：

```text
Session Core = Running
→ UI 根据 Running 状态决定按钮样式
```

## 5. 终端开发规范

### 必须测试

- 普通命令；
- 长时间运行命令；
- 持续大量输出；
- 交互式提示；
- Ctrl+C；
- resize；
- 中文输入与输出；
- ANSI 色彩；
- 程序异常退出；
- shell 内再启动子进程。

### 不允许

- 把 stdout 文本框伪装成完整终端；
- 因切换 Tab 销毁 PTY；
- 因主窗口隐藏暂停进程；
- 把 UI 渲染线程作为唯一读取输出的线程。

## 6. 进程停止规范

“停止”不能直接等同于 Kill。

建议顺序：

1. 请求优雅退出；
2. 等待超时；
3. 更新 UI 为 Stopping；
4. 超时后根据配置提示强制结束；
5. 强制结束时针对受管进程树；
6. 确认退出后再进入 Stopped / Exited。

不得因为父进程退出就盲目假定所有子进程已经结束。

## 7. 日志开发规范

所有日志相关实现必须遵守 `docs/LOGGING.md`。

特别强调：

- 终端缓冲区不是日志文件；
- 默认不记录交互 stdin；
- 普通终端默认不落盘；
- external log 不重复复制；
- 每次运行有独立 run_id；
- 日志路径必须可人工理解；
- retention 不能全局无差别清理。

新增日志模式前必须说明：

- 何时创建文件；
- 写什么；
- 何时关闭；
- 如何找到；
- 如何清理；
- 是否记录用户输入。

## 8. 配置兼容性

在 MVP 前期，配置格式可以调整。

一旦首次稳定版本发布：

- 新字段应提供默认值；
- 旧字段弃用需要迁移期；
- 不应静默改变危险行为；
- 破坏性配置变更必须记录在 changelog。

## 9. 错误处理

错误信息至少包含：

- 哪个 session；
- 什么操作；
- 失败原因；
- 可行动建议（若能确定）；
- 相关路径或命令。

例如：

```text
[ComfyUI] 启动失败
工作目录不存在：
D:\Tools\ComfyUI_windows_portable
```

比：

```text
Launch failed: error 2
```

更符合项目目标。

底层错误码可以作为详情保留。

## 10. 性能规范

### 避免

- 100ms 级别不断扫描全部进程；
- 不可见终端持续高频重绘；
- 每次输出一行就同步刷磁盘；
- 每个 Session 启动多个无必要监控线程；
- 全量重复读取日志文件。

### 推荐

- 事件驱动；
- 增量读取；
- 批量 UI 更新；
- 有界缓冲；
- 可配置低频健康检查；
- 日志写入缓冲。

## 11. 安全与隐私

### 禁止默认行为

- 记录用户所有键盘输入；
- 扫描并接管系统所有终端；
- 自动上传日志；
- 把日志写入公开或不可预测目录；
- 未提示就删除用户应用自身日志。

### 敏感信息

日志、命令和环境变量可能包含：

- API Key；
- Token；
- Cookie；
- 本地隐私路径；
- 用户输入内容。

Hub 不应主动把环境变量完整写入日志元数据。

## 12. Git 与提交规范

推荐 Conventional Commits 风格：

```text
feat: add interactive PowerShell session
fix: keep PTY alive when window is hidden
docs: define logging retention policy
refactor: separate process lifecycle from UI
test: cover graceful stop timeout
chore: update dependencies
```

一次提交尽量只完成一个逻辑主题。

## 13. 分支与 PR

早期个人开发可以保持简单：

- `main`：始终保持可构建；
- 功能分支：`feat/<name>`；
- 修复分支：`fix/<name>`。

PR 至少说明：

- 做了什么；
- 为什么；
- 如何测试；
- 是否影响进程生命周期；
- 是否影响日志；
- 是否改变配置格式。

## 14. 测试策略

### 单元测试

优先覆盖：

- 状态机；
- 配置解析；
- 日志策略；
- 日志路径生成；
- retention；
- 进程退出状态映射。

### 集成测试

优先覆盖：

- 启动 shell；
- 输入输出；
- Ctrl+C；
- 多 session；
- 重启；
- 优雅停止；
- 强制结束；
- 托盘隐藏后继续运行。

### 手工场景

至少维护：

- SillyTavern；
- ComfyUI；
- PowerShell；
- 长输出命令；
- 需要输入的测试程序；
- 异常退出程序。

## 15. Definition of Done

一个功能完成前，应确认：

- [ ] 功能行为明确；
- [ ] 不破坏其它会话；
- [ ] 对交互终端输入没有回归；
- [ ] 日志行为符合预期；
- [ ] 错误信息可理解；
- [ ] 不引入明显空闲 CPU 占用；
- [ ] 相关文档已更新；
- [ ] 有测试或明确的手工验证步骤。

## 16. 产品判断

当“通用性”和“可控性”冲突时，早期优先可控性。

当“更多信息”和“更低占用”冲突时，只保留真正帮助判断的信息。

当“自动化”和“可预测性”冲突时，优先可预测性。

Local Console Hub 应该让用户更清楚机器上正在运行什么，而不是再制造一层难以理解的自动行为。
