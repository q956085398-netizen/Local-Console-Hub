# #67 关联 Hub 外已运行的应用：Windows 实测记录

这份文档回答一个问题：**用户已经在 Hub 之外启动了某个应用，再从 Hub 点它的条目时，Hub 到底
做了什么**——以及**什么情况下它拒绝替你决定**。判定规则与取舍写在
`docs/DECISIONS.md` D-036，这里只记实测：一个真实的 debug 构建、真实的 Hub 外进程、真实的
CDP 驱动点击，逐条对照 #67 的验收标准。

结论先写在这里：三条主要路径（可靠识别 → 直接关联、不确定 → 提问、取消 → 什么都不变）与
「明确新开」都在真实窗口上跑通，进程数在每一次该不变的时候都没变。**未执行**的部分也逐条列在
§4：真正带窗口的应用（秋叶启动器 / ComfyUI 那类）、权限不足的候选、托盘与任务栏，本机这次
没有覆盖。

---

## 1. 环境与步骤

- 构建：本工作树的 debug 构建（`cargo build`），前端由 `npm run dev`（端口 24120）提供；
  窗口用 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS="--remote-debugging-port=9333"` 启动，
  经 CDP（Node 内置 `WebSocket`）读取 DOM、发真实鼠标事件、截图。
- 配置：把用户真实的 `%APPDATA%\LocalConsoleHub\config.yaml` 备份为
  `config.yaml.lch67-backup` 后换成一份只含一条窗口条目的验收配置；验收结束后按原样放回，
  `sha256sum` 与备份一致（`11b4c073…453f4e8`），备份文件已删除。
- 被认可的"应用"：`%TEMP%\lch67-fixture\lch67-demo.exe`——一份 `ping.exe` 的拷贝，取一个
  机器上不存在的名字，所以"候选"只可能是这次测试自己起的那些。命令写的是
  `"…\lch67-demo.exe" -n 120 127.0.0.1`，参数与进程实际命令行一致。

## 2. 对照 #67 的验收标准

| 标准 | 操作 | 实测结果 |
| --- | --- | --- |
| 不确定时显示有意义的候选 | Hub 外起两份同样的进程，在 Hub 里点「启动 Demo Launcher」 | 弹出对话框：「有 2 个进程都在运行这条配置指定的程序，Hub 无法确定哪一个才是你要打开的」，两条候选各带 PID、映像全路径与"还有别的进程在运行同一个程序"。**没有启动任何进程**（进程列表仍是那两份） |
| 可靠识别时关联，不额外创建进程 | 只留一份外部进程，点同一个入口 | **不提问**，直接关联：列表显示运行中，PID 就是外部那个（99012），进程数前后都是 1。`run_id` 为空、没有日志——Hub 没有创建运行 |
| 关联使用进程自己的时间 | 上一步之后看详情 | `up 46s`——那两行的时间来自进程的创建时间（`FILETIME`），不是"刚才" |
| 关联不扩大停止范围 | 关联后看头部控件 | 主控是「打开」，「停止」不出现，「重启」可见但禁用；托盘的全量操作按快照的 `external` 过滤（`tray::actions` 的用例钉住） |
| 无窗口时反馈真实结果 | 关联后点「打开」 | 状态栏如实说「应用已经在运行，但现在没有可以唤起的窗口。… Hub 不会为此再启动一份」——这个 fixture 本来就没有窗口 |
| 外部实例结束会被察觉 | 结束那份外部进程 | 那一行回到 `Exited`，PID 变成 `—`，计数回到 0 运行 |
| 明确新开 | 两份外部进程 → 提问 → 「新开一份」 | 出现第三份进程（103148），是 Hub 自己启动的那次运行；原来两份一个都没被碰 |
| 取消保持原应用及配置不变 | 两份外部进程 → 提问 → 「取消」 | 对话框关闭，进程数前后都是那两份，会话状态没有变化 |
| 无关同名应用不被牵连 | —— | 未执行（见 §4）：本机没有第二个同名文件可造，判定那一半由 `app::external::tests` 的合成用例覆盖 |

## 3. 视觉与结构

对话框与「添加应用」「保存启动配置」共用同一份 `dialog.css` 皮肤（同一层模态、同一组按钮、
同一套 `index.css` 令牌），新增的只有候选列表本身。截图与逐项比对：
标题是「「<应用名>」可能已经在运行」，正文先说 Hub 为什么不确定，再说明关联与启动是两件事，
每一条候选一张卡片（单选 + 名称/标题 + PID + 映像路径 + 不确定的原因），页脚三个按钮
`取消` / `新开一份` / `关联选中的实例`。字号、间距、圆角、颜色语义都取自共享令牌，没有引入
新的数值——这是它看起来和另外两个对话框是一套的原因，也是这次比对的判据（参考图
`assets/ui/ui-v2-service.png` 覆盖的是工作区，不含模态）。

## 4. 未执行的部分

- **真正带窗口的应用**（用户举的秋叶启动器 / ComfyUI）。本次用的 fixture 是控制台程序且没有
  自己的窗口，所以"把窗口带到前面"的 `Focused` / `Refused` 两个结果**没有被观察到**，
  观察到的是 `NoWindow`。这三条分支的实现是 D-034 已经验收过的那段（#66 的
  `WindowStep`），本片只是让它对着外部实例工作。
- **权限不足**（Hub 未提权、应用已提权）——本机这次没有构造。它属于"不确定"那一类，会作为
  不可关联的候选列出来，由 `app::external::tests` 的合成用例与对话框用例覆盖。
- **托盘、任务栏、系统级前台切换**：CDP 只能驱动 WebView 内容。托盘菜单的行为由
  `tray::actions` 的用例钉住，但"点托盘图标"这个动作本身没有执行。
- **H11 的完整矩阵**（同一应用的不同启动方式、PID 重用真的发生）没有全部走一遍：PID 重用
  无法按需制造，它由 `ProcessIdentity` 的创建时间核对与
  `app::external::native_tests::choosing_a_candidate_is_re_verified_against_its_creation_time`
  这一条钉住。

## 5. 一次真实的环境问题（记录，与本片无关）

跑全量 `cargo test` 时，本机上反复出现 `STATUS_DLL_INIT_FAILED (0xC0000142)`：测试自己起的
子进程在启动阶段就死掉。同时段的机器状态是 542 个进程、**70 个 `conhost`、13 个 `cmd`**——
正是 `docs/DECISIONS.md` D-035（#82，尚未并入本分支）描述的那种"受监督的一次运行在桌面上留下
一个控制台窗口"的堆积，桌面堆被耗尽。受影响的不只是本片新增的用例：`process::independent`
的控制台窗口用例、`session::core` 的终端进程树用例同样间歇失败——**都是本片没有碰过的模块**，
而且每一条单独跑都通过。把并行度降到 `--test-threads=4` 之后，531 条全过
（`106.12s`，`0 failed`）；默认并行度下失败的那一批，失败点全部是"起不来子进程"这一类。
这解释了本机全量测试的不稳定，也说明它不是本片引入的。本片新增用例在这一点上也做了让步：
真实进程的用例会**先等到进程表里真的能看见那个进程**再断言，因为进程表是活机器上的一次读数，
产品在"用户点开条目"的那一刻取它（那时应用已经跑了几秒），用例则在微秒之后就取。
