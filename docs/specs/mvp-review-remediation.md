# 补齐 MVP 审查发现：日志状态、配置诊断、会话同步与进程监管

状态：测试边界已确认，已发布为 GitHub issue #51，标记 `ready-for-agent`。

## Problem Statement

当前 MVP 的主要模块已实现，但用户仍可能遇到：开始记录后界面仍显示未记录、日志保存失败却收到成功提示、配置写错后会话静默消失、初始化期间会话状态落后于后台，以及服务停止后可能遗留快速创建的子进程。发布说明还将已经实现的终端用途与关闭影响字段列为缺失，无法准确回答产品完成到哪一步。

本规格依据 `main@015c44b` 的全仓审查。进程归属与初始化顺序问题是静态确认的竞态窗口，尚未动态复现；实现工作应先建立能够暴露问题的行为验证，不应把推断表述为已发生事故。

## Solution

让日志操作反馈真实结果、配置问题可见且可修复、初始会话列表与后续事件保持一致，并保证服务开始执行前已经属于受管进程树。同步完成情况文档，明确区分功能实现、自动化通过、原生验收和安装包验收。

本次修复完成不自动等于正式发布：未执行的 Windows 原生与安装版验收必须继续如实保留。

## User Stories

1. As a 交互终端用户, I want 开始记录后立即看到真实记录状态, so that 我知道输出是否正在落盘。
2. As a 交互终端用户, I want 开始记录后可以直接停止记录, so that 我能控制记录范围。
3. As a 交互终端用户, I want 停止记录后界面立即显示已停止, so that 我不会误认为仍在保存输出。
4. As a 服务用户, I want 保存本次日志后看到实际文件入口, so that 我能找到本次运行的诊断信息。
5. As a 用户, I want 日志写入失败时看到具体原因而非成功提示, so that 我能修复目录或权限问题。
6. As a 用户, I want 日志操作失败后保留真实会话状态, so that 文件错误不会被误解成进程退出。
7. As a 用户, I want 快速连续操作也不会让旧结果覆盖新状态, so that 我能信任当前记录指示。
8. As a 用户, I want 切换会话后不会收到上一会话的状态覆盖, so that 操作对象清晰可靠。
9. As a 配置维护者, I want YAML 格式错误能够显示位置或具体原因, so that 我能修复文件。
10. As a 配置维护者, I want 每个非法会话都有可辨识的错误, so that 我知道哪个配置项需要修改。
11. As a 配置维护者, I want 一条坏会话不隐藏其它合法会话, so that 我能继续使用正常服务。
12. As a 新用户, I want 缺少配置文件与配置读取失败呈现不同结果, so that 我不会把权限错误误当作空配置。
13. As a 用户, I want 启动窗口或恢复连接时显示后台最新会话状态, so that 我不会对过期状态采取操作。
14. As a 托盘用户, I want 初始化窗口期间的启停事件也被正确反映, so that 托盘和主窗口不会长期矛盾。
15. As a 用户, I want 初始化读取或订阅失败后能够明确获知并恢复, so that 界面不会永久停留在错误的预览状态。
16. As a 服务用户, I want 启动时立即创建的子进程也归属受管树, so that 停止不会遗漏后台工作。
17. As a 服务用户, I want 重启必须等旧受管树全部结束, so that 不会出现重复实例或端口占用。
18. As a 用户, I want 进程归属建立失败时清理这次启动产生的进程, so that 失败启动不会留下无人管理的进程。
19. As a 用户, I want 停止受管服务绝不影响其它进程, so that 我的其它工作保持安全。
20. As a 发布维护者, I want 文档准确列明已实现功能与待验项目, so that 工单关闭不会被误当成验收完成。
21. As a 用户, I want 终端用途和关闭影响的说明与实际配置能力一致, so that 我能正确配置和判断停止影响。

## Implementation Decisions

- Session Core 继续作为生命周期与运行状态的唯一事实来源；前端不推断进程是否已停止。保留现有技术栈、日志默认值和会话状态模型。
- 日志命令保留明确的操作语义。消费命令返回的日志状态，或在成功后重新读取权威状态；必须检查业务错误而不只检查 Promise 是否拒绝。只有状态确认成功后才显示成功提示。
- 日志状态、文件入口与可用按钮同步更新；较旧请求不得覆盖较新结果，已离开的会话不得接受迟到更新。避免通过全局高频轮询修补一致性。
- 启动加载保留文件级与逐会话配置诊断，并通过明确、只读的配置报告接口呈现给 UI。优先复用现有配置报告 DTO；诊断应包含会话标识或配置位置、失败字段及可操作原因。
- 缺少配置文件继续按首次安装处理；不可读取、格式错误与逐项验证错误不能伪装成普通空列表。保留合法会话可用性，不写回或修复用户配置。
- 会话初始化先建立可靠事件订阅，再读取初始数据；初始化期间事件不得丢失或被较旧快照覆盖。若采用事件缓存或版本机制，明确排序、过期结果拒绝、取消与失败恢复语义。
- 服务执行用户程序前必须完成 Job 归属。可选择挂起创建后归属再恢复，或创建时指定 Job；实现前确认 Windows API 与现有启动封装的适用性，不在规格阶段锁定未经验证的调用方案。
- 归属失败必须清理本次启动资源；停止和重启只依赖明确拥有的进程树，禁止按可执行文件名全局终止进程。保留优雅停止、超时升级与显式强制结束的现有区别。
- 遵守 D-007、D-009、D-018、D-020、D-025、D-027：服务停止与终端 Ctrl+C 不混淆；连接存活与会话状态不混淆；终端用途与关闭影响继续是共有字段。
- 更新发布说明与项目介绍中已过时的完成情况。记录每项原生验收的实际结果和适用版本，不用测试通过代替用户可见验收。
- 本规格覆盖五个独立问题；配置诊断在两条审查轴上的重复发现只修复一次。修复实现与发布门槛证据分别记录。

## Testing Decisions

- 好的测试检查用户可观察结果、资源归属和异步顺序，不断言内部函数调用形状，不用镜像实现的单测替代端到端行为。
- 优先使用两个现有高层边界：Session Core 的真实 Windows 集成边界，以及前端连接/终端附着协议已经采用的可注入后端边界。无需为每个文件各建一层 mock。
- 后端通过临时配置加载到应用注册与配置报告的完整链路，验证坏 YAML、读失败、非法会话、合法与非法混合、首次安装，以及错误的具体可辨识性。只测试解析器不足以证明错误已经传到界面。
- 真实 Windows 进程验证：启动后立即创建子进程、快速父进程退出、归属失败、停止、重启以及无关哨兵进程存活。使用可协调的测试程序或握手缩小竞态验证的不确定性；重复压力通过不是唯一正确性证明。
- 前端若缺少可直接驱动的控制边界，只提取最小的异步协调逻辑，让现有 hook 成为薄适配器。沿用连接恢复与终端附着测试的思路，暂不引入全仓 DOM 测试框架。
- 日志行为覆盖开始、停止、保存、业务错误、请求乱序、切换会话与销毁。断言最终状态、按钮动作含义、文件路径和提示；命令成功但返回 last_error 时不得显示成功。
- 初始化行为覆盖订阅建立前后、快照读取期间、两个初始请求不同完成顺序、迟到事件、取消及失败恢复。断言最终模型与最新后台事实一致，并保持有界资源使用。
- 原生 Windows 验收补验手动日志按钮与错误提示、配置诊断展示、初始化期间托盘启停、终端用途/关闭影响。浏览器预览与协议测试不算这些项目通过。
- 运行现有前端测试、类型检查、Lint、格式与构建，以及 Rust 测试、格式与 Clippy。保留测试环境和并发模式，避免将沙箱或时序失败直接认定为产品回归。
- 自动化完成条件：新增回归能暴露修复前行为、修复后通过且既有检查通过。原生部分按通过/失败/未执行分别记录；任何未执行项不得标为完成。

## Out of Scope

- 新增图形配置编辑器、自动重载配置、全局接管系统终端或后台进程。
- HTTP 健康检查、Busy 适配器、跨平台支持、代码签名及新的发布渠道。
- 全面 UI 重设计、引入全仓 DOM 测试框架或无关结构重构。
- 更改日志默认隐私策略、自动上传日志、删除外部应用日志或用户配置。
- 本规格发布阶段不修改实现、不发布安装包、不把原生或 MSI 待验项自动关闭。
