# 日志规范

Local Console Hub 的日志设计目标是：

> **需要时能留下、留下后找得到、找到了看得懂；不需要时不要因为“开了终端”就自动生成一堆文件。**

日志不是所有会话的默认副作用，而是一项有策略的能力。

## 1. 基本原则

### 1.1 终端显示 ≠ 持久化日志

用户在 UI 中看到输出，不代表这些输出一定写入磁盘。

所有会话都可以拥有有限大小的内存终端缓冲区，但是否写文件由日志策略单独决定。

### 1.2 交互终端默认不持久化

普通 PowerShell / CMD / pwsh / REPL 等交互会话默认：

- 保留内存缓冲；
- 不生成日志文件；
- 不记录 stdin；
- 用户可以为某次会话手动开启记录。

原因：

- 大量短生命周期 shell 生成日志没有价值；
- 交互内容可能包含路径、token、口令等敏感信息；
- 会产生难以管理的日志垃圾。

### 1.3 服务型会话可以按策略记录

例如 SillyTavern、ComfyUI、本地 API：

- 若应用本身没有日志，可由 Hub 捕获 stdout/stderr；
- 若应用已经有可靠日志文件，Hub 优先关联原日志；
- 如果服务输出价值不高，也允许关闭持久化。

### 1.4 用户必须知道“现在有没有在记录”

UI 中应明确展示：

- 日志状态：Off / Capturing / External / On Error；
- 日志位置；
- 当前运行对应的日志文件；
- 是否会记录用户输入。

不能出现“用户以为没记录，但实际上后台一直在写”的情况。

实现说明（T05）：

- 这四个状态描述的是该会话**当前生效的策略**。有运行在跑时以实时状态为准
  （`manual` 未开始记录时是 Off，点了“开始记录”才是 Capturing；
  `on_error` 提交了缓冲后即处于会写盘的状态）；
- 没有运行时显示的是“下一次启动会怎样”，而不是“此刻正在写”。因此
  「状态 = Capturing」在会话已停止时表示策略为一直记录，不表示磁盘上正在增长；
- 反过来绝不允许：只要 Hub 正在往文件里写，状态就必须是 Capturing / On Error / External
  之一，不能显示 Off。


## 2. 日志来源

每个会话最多可以配置一个主要来源类型：

### `none`

不持久化。

适合：

- 临时 shell；
- 普通 REPL；
- 无需追溯的短任务。

### `captured`

由 Hub 捕获进程 stdout/stderr。

适合：

- 没有独立日志文件的长期服务；
- 调试服务；
- 希望统一检索的程序。

### `external`

应用自己写日志，Hub 只负责建立关联和入口。

例如：

```yaml
logging:
  source: external
  path: D:/Tools/SillyTavern/data/access.log
```

Hub 不应为了“统一”再复制一份相同内容。

## 3. 日志模式

建议支持：

### `off`

完全不持久化。

### `always`

每次运行都保存。

适合：

- 重要服务；
- 长期调试进程；
- 需要审查历史错误的程序。

### `on_error`

正常运行时只保留有限内存缓冲。

当发生以下情况之一时，将最近一段缓冲与后续退出信息写入文件：

- 退出码非 0；
- 状态进入 Error；
- 健康检查连续失败；
- 用户手动点击“保存本次日志”。

适合希望“平时不留垃圾，出问题时有证据”的服务。

### `manual`

默认不写。

用户在 UI 中点击“开始记录”后才写，停止记录后关闭文件。

适合：

- 临时调试；
- 交互式测试；
- 难复现问题。

### `auto`

由 Hub 根据会话类型选择合理默认值。

初期建议：

- Interactive Terminal → `off`
- Service Session 且 source=external → 使用 external，不额外捕获
- Service Session 且无 external log → `on_error`
- 用户显式配置 → 以用户配置为准

`auto` 只是默认推导，不应包含难以预测的“智能决策”。

## 4. stdin 处理

### 默认规则

**不记录 stdin。**

即使 stdout/stderr 正在持久化，也不代表用户输入应该被写入日志。

这是为了避免：

- token；
- password；
- API key；
- 私密命令；
- 临时粘贴的数据

被无意保存。

未来如果加入输入记录能力，必须：

- 显式开启；
- 在 UI 中持续显示明显状态；
- 支持快速关闭；
- 文档中说明风险。

## 5. 推荐目录结构

Hub 自己生成的日志应集中在一个固定根目录。

Windows 初期建议使用用户数据目录，而不是项目安装目录，例如：

```text
%LOCALAPPDATA%/LocalConsoleHub/
├─ logs/
│  ├─ comfyui/
│  │  ├─ 2026-09/
│  │  │  ├─ 2026-09-24_09-30-15__run-8f31.log
│  │  │  └─ 2026-09-24_14-02-01__run-c8aa.log
│  ├─ sillytavern/
│  └─ test-api/
├─ metadata/
└─ cache/
```

目录层级原则：

1. 按 `session_id` 分类；
2. 按年月分层，避免单目录文件过多；
3. 每次运行拥有独立 `run_id`；
4. 文件名包含时间，方便人工查找；
5. 不依赖 UI 数据库才能看懂文件归属。

## 6. 运行元数据

每次受管运行应拥有一个 `run_id`。

建议记录少量结构化元数据，例如：

```json
{
  "run_id": "8f31",
  "session_id": "comfyui",
  "started_at": "2026-09-24T09:30:15+08:00",
  "ended_at": "2026-09-24T11:12:41+08:00",
  "exit_code": 0,
  "pid": 12345,
  "log_mode": "always",
  "log_source": "captured",
  "log_file": "logs/comfyui/2026-09/2026-09-24_09-30-15__run-8f31.log"
}
```

元数据用于：

- UI 历史运行列表；
- 快速定位日志；
- 搜索；
- 清理策略；
- 后续故障分析。

不要把大量运行输出塞进元数据文件。

实现说明（T10）：

- 元数据文件**只写不删**。保留策略清理的是日志文件
  （`logs/<session>/<YYYY-MM>/*.log`），元数据在另一个根目录
  （`metadata/<session>/<YYYY-MM>/`），任何清理都不会触及它。「这次运行发生过」本身就是
  记录，不能因为它的日志过期而一起消失；
- 因此运行历史里允许出现「记录还在、日志文件已经不在」的行。`get_run_history` 的每条记录
  在 `RunRecord` 原有字段之外多一个 `logFilePresent`（布尔）：该记录指向的文件此刻是否真的
  在磁盘上。读法是「`logFile` 有值 **且** `logFilePresent` 为 `true`」才表示有文件可打开；
  两者都为假才是「本次运行没有落盘」；
- `logFilePresent` 只存在于读取路径（IPC 载荷），**不写进元数据文件**：落盘的文档仍然是与
  前端同形的 `RunRecord`（D-016），磁盘上的文档不会因为这条运行时信息而分叉；
- 在磁盘上直接把日志文件删掉会得到同样的结果——这个判断按文件系统的当前事实回答，
  不追溯「是谁删的」。

## 7. 日志内容格式

初期优先使用 UTF-8 纯文本。

建议：

- 每次运行一个文件；
- 保留必要的时间戳；
- 保留 stdout/stderr 来源信息的能力；
- 搜索视图可以去除 ANSI 控制字符；
- 终端显示仍然保留 ANSI 效果。

可以后续评估 NDJSON，但 MVP 不要求。

## 8. 终端缓冲区

即使 `logging.mode=off`，UI 仍可以保留有限内存缓冲。

建议：

- 每会话限制最大行数或最大字节数；
- 环形缓冲；
- 超出后丢弃最旧内容；
- 不自动写磁盘；
- Hub 隐藏到托盘时仍可继续收集；
- Hub 真正退出后不保证保留。

`on_error` 模式可以利用该缓冲，在错误发生时将“错误前 N 行”补写到日志。

实现说明（T05）：

- 缓冲按会话（session）持有，不按运行（run）持有，因此重启服务不会清掉用户正在看的内容；
- 会话快照里只携带摘要（字节数、行数、已丢弃字节数），完整内容按需读取，
  避免每次状态变化都复制整段回滚缓冲；
- 被丢弃的字节会被计数并暴露出来，UI 可以据此说明「更早的输出已被丢弃」，
  而不是呈现一段有缺口的回滚历史；
- 持久化日志与内存缓冲是两条独立的路径：`mode: off` 只表示不写文件，
  不表示不收集。

## 9. 轮转与保留

必须避免日志无限增长。

至少支持：

- 单文件最大大小；
- 最大保留天数；
- 每会话最大总大小；
- 手动清理。

清理必须按 session 分类，不应让某个高输出服务挤掉其它所有会话的日志。

### 实现阶段确定的默认值（T05 落地）

- 单次运行的日志文件上限 **16 MiB**：达到上限后截断，并在文件里写明「已截断」，
  不静默停止；
- 每会话日志总量上限 **256 MiB**：超出时按最旧优先删除，**最近一次运行的文件始终保留**；
- 保留天数 **30 天**（`0` 表示不启用按天清理）；
- 终端缓冲 **256 KiB / 5000 行**；`on_error` 的错误前缓冲 **64 KiB / 2000 行**。

这些值目前不是配置项：改变它们会改变用户磁盘占用，应当是一个明确的产品决定，
而不是一个可以随手改的开关。

清理只作用于 Hub 自己的日志根目录（`logs/<session_id>/<YYYY-MM>/*.log`）。
`source: external` 指向的应用自有日志不在该目录下，永远不会被清理删除。

清理删除的**只有日志文件**：运行元数据（`metadata/…`）不在清理范围内，也不会被连带删除
（§6 实现说明）。清理之后仍留在运行历史里的行会标明它的日志文件已经不在，而不是给出一个
点下去就失败的操作。

## 10. 日志发现与 UI

用户应能从以下入口找到日志：

### 从会话

`会话 → 日志 → 当前运行 / 历史运行`

### 从运行历史

`会话 → Runs → 某次运行 → 打开日志文件`

### 从文件系统

目录结构本身可读，用户不需要 Hub 也能定位。

UI 至少提供：

- 打开日志；
- 打开所在文件夹；
- 复制路径；
- 清理旧日志；
- 显示当前策略。

实现说明（T10）：

- 路径由 Session Core 解析，前端只提交 `session_id`（+ 可选 `run_id`）；命令不接受
  路径参数，因此界面无法变成通用文件启动器（D-021）；
- 「打开日志 / 打开所在文件夹 / 复制路径」同时出现在当前运行与历史运行的每一行上：
  当前运行常常还没有元数据记录（记录在运行结束时才落盘），历史行则各自指向自己那一份；
- 清理是两步：`preview_log_cleanup` 先给出「将删除 N 个日志文件 · 释放 X · 最近一次运行
  始终保留 · 运行历史记录不会被删除」，用户确认后才执行 `cleanup_logs`；删除失败的文件
  会被报出来，而不是显示成清理成功；
- 运行历史的每一行区分三种情况：有文件可打开、本次运行没有落盘（显示 `未落盘`）、
  记录指向的文件不在磁盘上（行内显示「日志文件不在磁盘上（运行记录保留）」，并且只保留
  「打开所在目录」——目录在清理后仍然存在，而「打开日志/复制路径」指向的文件已经不在了）。
  措辞只说事实、不猜原因：这一行分不清「被保留策略清掉了」和「`external` 的应用还没写出
  那个文件」，而替用户断定一个它没有观察到原因，正是这个页面试图避免的编造；
- 界面明确标注数据来源：会话已注册于 Core 时显示「后端实时」，否则回退到预览数据并
  标注「预览数据」。两者不会混在一屏里（§1.4：不允许出现「以为没记录」的错觉）。

## 11. External Log 的处理

对于应用自身日志，Hub 应优先做“链接”而不是“复制”。

需要考虑：

- 文件可能滚动；
- 路径可能是相对路径；
- 一个服务可能有多个日志；
- 某些日志由应用自身维护保留策略。

实现说明（T05）：`source: external` 的会话**不接入 Hub 的内存缓冲**。Hub 既不写盘也不接收
它的 stdout/stderr，因为它要展示的那份内容由应用自己维护；同时接收一份“可能不完整”的副本，
只会造成两份时间线不一致（D-005）。因此该会话的 UI 入口只有一个：打开应用自己的日志文件。

后续可以支持：

```yaml
logging:
  source: external
  files:
    - name: access
      path: data/access.log
    - name: error
      path: data/error.log
```

MVP 可以先只支持单个主日志文件。

## 12. 建议配置草案

### 普通交互 shell

```yaml
logging:
  mode: off
  source: none
```

### 长期服务，由 Hub 保存

```yaml
logging:
  mode: always
  source: captured
```

### 只在出错时保存

```yaml
logging:
  mode: on_error
  source: captured
```

### 应用已经自己写日志

```yaml
logging:
  mode: always
  source: external
  path: ./data/app.log
```

## 13. 验收场景

### 场景 A：打开普通 PowerShell

- 可以输入命令；
- 可以回看近期输出；
- 关闭会话后磁盘中没有自动生成日志。

### 场景 B：ComfyUI 配置为 always

- 启动后创建一个 run；
- 输出持续写入对应 run 文件；
- UI 可以直接打开该文件；
- 重启后创建新的 run 文件，不覆盖旧文件。

### 场景 C：服务配置为 on_error

- 正常退出时不必留下完整日志；
- 异常退出时产生错误日志；
- 日志包含错误发生前的有限缓冲；
- UI 明确显示它是一次异常运行。

### 场景 D：应用已有日志

- Hub 显示 External；
- 可以一键打开原日志；
- Hub 不重复捕获相同输出。
