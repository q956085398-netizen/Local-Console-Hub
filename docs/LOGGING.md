# 日志规范

Local Console Hub 的日志设计目标是：

> **需要时能留下、留下后找得到、找到了看得懂；不需要时不要因为“开了终端”就自动生成一堆文件。**

日志不是所有会话的默认副作用，而是一项有策略的能力。

## 1. 基本原则

### 1.1 终端显示 ≠ 持久化日志

用户在 UI 中看到输出，不代表这些输出一定写入磁盘。

所有会话都可以拥有有限大小的内存终端缓冲区，但是否写文件由日志策略单独决定。

### 1.2 交互终端默认不持久化

普通 PowerShell / CMD / pwsh / REPL 等交互会话默认：

- 保留内存缓冲；
- 不生成日志文件；
- 不记录 stdin；
- 用户可以为某次会话手动开启记录。

原因：

- 大量短生命周期 shell 生成日志没有价值；
- 交互内容可能包含路径、token、口令等敏感信息；
- 会产生难以管理的日志垃圾。

### 1.3 服务型会话可以按策略记录

例如 SillyTavern、ComfyUI、本地 API：

- 若应用本身没有日志，可由 Hub 捕获 stdout/stderr；
- 若应用已经有可靠日志文件，Hub 优先关联原日志；
- 如果服务输出价值不高，也允许关闭持久化。

### 1.4 用户必须知道“现在有没有在记录”

UI 中应明确展示：

- 日志状态：Off / Capturing / External / On Error；
- 日志位置；
- 当前运行对应的日志文件；
- 是否会记录用户输入。

不能出现“用户以为没记录，但实际上后台一直在写”的情况。

## 2. 日志来源

每个会话最多可以配置一个主要来源类型：

### `none`

不持久化。

适合：

- 临时 shell；
- 普通 REPL；
- 无需追溯的短任务。

### `captured`

由 Hub 捕获进程 stdout/stderr。

适合：

- 没有独立日志文件的长期服务；
- 调试服务；
- 希望统一检索的程序。

### `external`

应用自己写日志，Hub 只负责建立关联和入口。

例如：

```yaml
logging:
  source: external
  path: D:/Tools/SillyTavern/data/access.log
```

Hub 不应为了“统一”再复制一份相同内容。

## 3. 日志模式

建议支持：

### `off`

完全不持久化。

### `always`

每次运行都保存。

适合：

- 重要服务；
- 长期调试进程；
- 需要审查历史错误的程序。

### `on_error`

正常运行时只保留有限内存缓冲。

当发生以下情况之一时，将最近一段缓冲与后续退出信息写入文件：

- 退出码非 0；
- 状态进入 Error；
- 健康检查连续失败；
- 用户手动点击“保存本次日志”。

适合希望“平时不留垃圾，出问题时有证据”的服务。

### `manual`

默认不写。

用户在 UI 中点击“开始记录”后才写，停止记录后关闭文件。

适合：

- 临时调试；
- 交互式测试；
- 难复现问题。

### `auto`

由 Hub 根据会话类型选择合理默认值。

初期建议：

- Interactive Terminal → `off`
- Service Session 且 source=external → 使用 external，不额外捕获
- Service Session 且无 external log → `on_error`
- 用户显式配置 → 以用户配置为准

`auto` 只是默认推导，不应包含难以预测的“智能决策”。

## 4. stdin 处理

### 默认规则

**不记录 stdin。**

即使 stdout/stderr 正在持久化，也不代表用户输入应该被写入日志。

这是为了避免：

- token；
- password；
- API key；
- 私密命令；
- 临时粘贴的数据

被无意保存。

未来如果加入输入记录能力，必须：

- 显式开启；
- 在 UI 中持续显示明显状态；
- 支持快速关闭；
- 文档中说明风险。

## 5. 推荐目录结构

Hub 自己生成的日志应集中在一个固定根目录。

Windows 初期建议使用用户数据目录，而不是项目安装目录，例如：

```text
%LOCALAPPDATA%/LocalConsoleHub/
├─ logs/
│  ├─ comfyui/
│  │  ├─ 2026-09/
│  │  │  ├─ 2026-09-24_09-30-15__run-8f31.log
│  │  │  └─ 2026-09-24_14-02-01__run-c8aa.log
│  ├─ sillytavern/
│  └─ test-api/
├─ metadata/
└─ cache/
```

目录层级原则：

1. 按 `session_id` 分类；
2. 按年月分层，避免单目录文件过多；
3. 每次运行拥有独立 `run_id`；
4. 文件名包含时间，方便人工查找；
5. 不依赖 UI 数据库才能看懂文件归属。

## 6. 运行元数据

每次受管运行应拥有一个 `run_id`。

建议记录少量结构化元数据，例如：

```json
{
  "run_id": "8f31",
  "session_id": "comfyui",
  "started_at": "2026-09-24T09:30:15+08:00",
  "ended_at": "2026-09-24T11:12:41+08:00",
  "exit_code": 0,
  "pid": 12345,
  "log_mode": "always",
  "log_source": "captured",
  "log_file": "logs/comfyui/2026-09/2026-09-24_09-30-15__run-8f31.log"
}
```

元数据用于：

- UI 历史运行列表；
- 快速定位日志；
- 搜索；
- 清理策略；
- 后续故障分析。

不要把大量运行输出塞进元数据文件。

## 7. 日志内容格式

初期优先使用 UTF-8 纯文本。

建议：

- 每次运行一个文件；
- 保留必要的时间戳；
- 保留 stdout/stderr 来源信息的能力；
- 搜索视图可以去除 ANSI 控制字符；
- 终端显示仍然保留 ANSI 效果。

可以后续评估 NDJSON，但 MVP 不要求。

## 8. 终端缓冲区

即使 `logging.mode=off`，UI 仍可以保留有限内存缓冲。

建议：

- 每会话限制最大行数或最大字节数；
- 环形缓冲；
- 超出后丢弃最旧内容；
- 不自动写磁盘；
- Hub 隐藏到托盘时仍可继续收集；
- Hub 真正退出后不保证保留。

`on_error` 模式可以利用该缓冲，在错误发生时将“错误前 N 行”补写到日志。

## 9. 轮转与保留

必须避免日志无限增长。

至少支持：

- 单文件最大大小；
- 最大保留天数；
- 每会话最大总大小；
- 手动清理。

默认值在实现阶段根据实际测试决定。

清理必须按 session 分类，不应让某个高输出服务挤掉其它所有会话的日志。

## 10. 日志发现与 UI

用户应能从以下入口找到日志：

### 从会话

`会话 → 日志 → 当前运行 / 历史运行`

### 从运行历史

`会话 → Runs → 某次运行 → 打开日志文件`

### 从文件系统

目录结构本身可读，用户不需要 Hub 也能定位。

UI 至少提供：

- 打开日志；
- 打开所在文件夹；
- 复制路径；
- 清理旧日志；
- 显示当前策略。

## 11. External Log 的处理

对于应用自身日志，Hub 应优先做“链接”而不是“复制”。

需要考虑：

- 文件可能滚动；
- 路径可能是相对路径；
- 一个服务可能有多个日志；
- 某些日志由应用自身维护保留策略。

后续可以支持：

```yaml
logging:
  source: external
  files:
    - name: access
      path: data/access.log
    - name: error
      path: data/error.log
```

MVP 可以先只支持单个主日志文件。

## 12. 建议配置草案

### 普通交互 shell

```yaml
logging:
  mode: off
  source: none
```

### 长期服务，由 Hub 保存

```yaml
logging:
  mode: always
  source: captured
```

### 只在出错时保存

```yaml
logging:
  mode: on_error
  source: captured
```

### 应用已经自己写日志

```yaml
logging:
  mode: always
  source: external
  path: ./data/app.log
```

## 13. 验收场景

### 场景 A：打开普通 PowerShell

- 可以输入命令；
- 可以回看近期输出；
- 关闭会话后磁盘中没有自动生成日志。

### 场景 B：ComfyUI 配置为 always

- 启动后创建一个 run；
- 输出持续写入对应 run 文件；
- UI 可以直接打开该文件；
- 重启后创建新的 run 文件，不覆盖旧文件。

### 场景 C：服务配置为 on_error

- 正常退出时不必留下完整日志；
- 异常退出时产生错误日志；
- 日志包含错误发生前的有限缓冲；
- UI 明确显示它是一次异常运行。

### 场景 D：应用已有日志

- Hub 显示 External；
- 可以一键打开原日志；
- Hub 不重复捕获相同输出。
